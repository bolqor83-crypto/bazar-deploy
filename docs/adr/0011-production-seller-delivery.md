# ADR 0011: Production readiness, кабинет продавца и доставки (Промт 10)

Дата: 2026-11-15
Статус: принято

## Контекст

Промт 9 оставил платформу с каталогом, корзиной и заказами на
PostgreSQL/Neon, но секреты жили в AsyncStorage, SMS-код был
заглушкой, деплоя не было, а продавец и перевозчик не имели
рабочих инструментов. Промт 10 закрывает четыре блока:

1. **Безопасность сессий и вход по SMS** (Часть A).
2. **Деплой на Render** через публичное зеркало (Часть A).
3. **Кабинет продавца**: S3-загрузки, товары, предложения,
   жизненный цикл заказов, уведомления (Части B–C).
4. **Доставки**: заявки по заказу, лента перевозчика, статусная
   машина рейса (Часть D — этот ADR фиксирует прежде всего её).

## Решение

### A. Безопасность и SMS (Часть A)

- **SecureStore**: refresh-токен — expo-secure-store (Keystore/
  Keychain), web — sessionStorage; миграция из AsyncStorage при
  первом запуске; access-токен только в памяти модуля.
- **SmsProvider**: интерфейс + dev-заглушка (код в ответе
  помечен `devOnly`), прод-провайдер — вне скоупа демо.
- **Rate limit OTP**: 3 попытки/10 мин на номер, 10/час на IP —
  поверх общего бакета 100/мин.

### B. Деплой на Render (Часть A)

- **Render Web Service** из публичного зеркала `bazar-deploy`
  (GitHub Actions синхронизирует туда main: у Render нет доступа
  к приватному репозиторию). Сборка: pnpm → expo export web →
  nest build → Prisma generate. Рантайм: `node dist/src/main.js`,
  статику mobile отдаёт ServeStaticModule, БД — тот же проект
  Neon (демо-контур), `migrate deploy` не выполняется — схема
  применяется разработчиком при изменениях.
- **Секреты** — env сервиса Render, загружены скриптом через
  Render API (значения не печатаются).

### C. Кабинет продавца (Части B–C)

- **S3/R2 presign**: PUT-URL на 10 минут, ключи `uploads/…`,
  валидация типа/размера на сервере; фото товара — прямой
  upload из клиента в бакет.
- **Товары**: `archivedAt` — soft-delete; организация-владелец
  (`organizationId`), системные товары сида — `null`.
- **Предложения**: `OfferPriceHistory` (аудит смен цены),
  `StockChange` (приход/расход/корректировка), архив и `stock=0`.
- **Заказы продавца**: статусная машина confirm → preparing →
  ready → complete (+ отмена из PENDING/CONFIRMED с возвратом
  stock), каждое действие — транзакция «статус + OrderEvent +
  уведомление». Список с фильтрами-чипами и поиском.
- **Уведомления**: модель Notification (type, payload-JSON,
  readAt), /api/notifications с unread-count и отметками;
  адресаты — контрагенты события (NEW_ORDER продавцам,
  ORDER_STATUS покупателю, отмена — обеим сторонам).

### D. Доставки (Часть D)

- **Модель**: `DeliveryRequest` (номер `DL-YYYY-NNNNNN` через
  `DeliveryCounter`, адреса/контакты забора и выгрузки, вес/
  объём/примечания, ставка `price`, `cancelReason`) +
  `DeliveryEvent` (аудит) + счётчик. Связи: Order (Restrict —
  заказ не удаляется молча при живых доставках), User-инициатор
  (Restrict), Organization-перевозчик (SetNull), события
  каскадом. **Одна активная заявка на заказ** (PENDING…DELIVERED).
- **Статусная машина**: PENDING → ACCEPTED → PICKED_UP →
  IN_TRANSIT → DELIVERED → COMPLETED. Отмена: инициатор
  (buyer/seller) из PENDING, перевозчик из ACCEPTED — с
  обязательной причиной.
- **Роли**: заявку создаёт покупатель или продавец заказа
  (статус CONFIRMED/PREPARING/READY); принимает и ведёт рейс
  **организация-перевозчик** — любой член с ролью CARRIER
  (командная модель: диспетчер принял, водитель ведёт);
  завершает только покупатель (подтверждение получения).
- **Атомарность принятия**: `updateMany WHERE status='PENDING'`
  в транзакции — гонку двух перевозчиков выигрывает ровно один;
  опоздавший получает 404, повтор своей организации — 400.
- **Каждый переход** — транзакция: статус + DeliveryEvent +
  уведомления участникам (покупатель, инициатор, продавцы
  организации — они передают груз на заборе, перевозчики).
  Типы: NEW_DELIVERY, DELIVERY_STATUS, DELIVERY_CANCELLED.
- **API**: POST/GET /api/deliveries (участники), :id/complete,
  :id/cancel {reason}; GET /api/carrier/deliveries?scope=feed|
  mine + :id + accept {price?} / picked-up / in-transit /
  delivered — за CarrierMembershipGuard (X-Organization-Id).
- **Мобильные экраны**: лента заявок с «Принять» (диалог ставки),
  «Мои доставки» (Активные/История, кнопка шага рейса на
  карточке — в зоне большого пальца), История с заработком,
  карточка доставки (DeliveryTimeline + действия по роли),
  блок «Доставка» в заказе покупателя и продавца (форма заявки
  или карточка активной доставки).

### Отказ от платных перевозок и платежей

Доставка — заявочная, без расчётов и эскроу: ставка фиксируется
при принятии как ориентир для сторон. Оплата — Промт 11.

## Альтернативы

- **Перевозчик-пользователь вместо организации** — отвергнуто:
  логистика работает командой, смена диспетчера не должна
  рвать рейс; членство уже проверяет guard.
- **Несколько заявок на заказ с выбором перевозчика (тендер)** —
  отвергнуто до спроса: удваивает модель без подтверждённой
  потребности рынка; одна активная заявка проще и предсказуемее.
- **DeliveryStatus как enum Postgres** — отвергнуто: проект
  держит статусы строками (наследие SQLite-эпохи, ADR 0008),
  значения валидируются DTO и сервисом.

## Последствия

- e2e `clearDatabase` чистит доставки до заказов (RESTRICT на
  orderId), события уходят каскадом.
- Экран «Доставки» покупателя остаётся заглушкой до Промта 11
  (списка доставок покупателя в API нет — вход через заказ).
- Тестовая БД bazar_test пересоздаётся `db push` — схема
  доставок применяется автоматически, миграции не нужны.
- Числа на каждом прогоне: api unit 164, e2e 94, ui 248,
  mobile 344 — 850 тестов, 16/16 turbo-задач.

## Открытые вопросы (Промт 11)

- Оплата и взаиморасчёты (эскроу, чеки, комиссии доставки).
- Push-уведомления вместо in-app ленты.
- Группировка заказов точки в один рейс (маршруты перевозчика).
- Аналитика для продавца и перевозчика.
- Next.js-витрина (веб-клиент поверх того же API).
