# ADR 0005: Пост-аутентификационная маршрутизация и онбординг

- **Статус:** принято (Промт 6, части A и B)
- **Дата:** 2026-11-11

## Контекст

После аутентификации пользователь попадает в одно из двух состояний:
с членствами (готов работать) или без них (нужна настройка). До Промта 6
навигацию после входа выполняли сами экраны: `register` звал
`router.replace('/welcome')`, `login` и `otp` — `router.replace('/(tabs)')`.

### Баг №2 (закрыт в Части A)

Воспроизводилось стабильно: после регистрации экран `/welcome`
пропускался, пользователь оказывался в `/(tabs)`.

Гонка: `register()` выставляет `state: 'authenticated'` **до** возврата
в экран; `(auth)/_layout` перерисовывается, `AuthGuard(requireAuth=false)`
монтирует `<Redirect href="/(tabs)" />` — и этот переход выигрывает у
последующего `router.replace('/welcome')` экрана. Пока в `(auth)` было
исключение для `/welcome` по `usePathname`, оно не помогало: редирект
срабатывал раньше, чем навигация на `/welcome` вообще начиналась.

## Решение

### 1. Guard — единственный маршрутизатор после входа

`AuthGuard` в гостевой зоне (`requireAuth=false`) при
`state === 'authenticated'` смотрит на членства:

- есть членства → `/(tabs)`;
- нет членств → `/welcome` (онбординг).

Ручные `router.replace(...)` из экранов `login`, `otp`, `register`
удалены. Гонка исчезает как класс: нечего перебивать. Рассматривалась
альтернатива — «guard не редиректит без членств, экраны навигируют
сами», — отклонена: она требует дублировать переход в трёх экранах и
возвращает гонку при любом пропуске.

### 2. Группа `(onboarding)`

Новый сегмент маршрутов: `welcome`, `role`, `organization`, `location`,
`done`. Старый `(auth)/welcome.tsx` удалён (заглушка Промта 4). Путь
`/welcome` сохранился — группа не входит в URL.

`OnboardingGuard`: `unknown` → скелетон; не аутентифицирован →
`/login`; есть членства → `/(tabs)`; иначе — пропускает. Циклов с
`AuthGuard` нет: каждый guard смотрит только на своё условие.

### 3. Поток шагов

`role → organization → (только store_owner) location → done`;
`customer` после роли идёт сразу в `done`. Членство создаётся **только
в `finish()`** — брошенный на полпути онбординг можно возобновить:
`OnboardingGuard` пускает пользователя без членств, повторный вход
попадает на сохранённый шаг.

### 4. Состояние — `onboardingStore`

Персист `bazar.onboarding.state` (шаг, роль, черновики форм, id
созданных сущностей): после перезагрузки — тот же шаг и заполненные
формы. Действия поглощают ошибки: русский текст в `state.error`,
исключения наружу не летят.

`finish()`:

1. `onboardingMockService.addMembership` (идемпотентен);
2. `authStore.refreshUser()` — новый метод: `getSession` по активному
   токену без перечитывания хранилища сессии; обновляет `user` и
   синхронизирует `contextStore`;
3. `contextStore.setRole(role)` (+ `setLocation` для store_owner).

### 5. «Снимок мира» в contextStore

`contextStore` теперь держит `organizations` и `locations` (по умолчанию
моки Промта 3) и персистит их вместе с `active` и `memberships`.
Созданные в онбординге сущности регистрируются
`registerOrganizations/registerLocations` и видны шапке и шиту выбора
сразу; после перезагрузки контекст валиден без обращения к бэкенду —
валидация точек идёт по известному списку, а не только по мокам.
Гостевой контекст по-прежнему `userId: ''` — семантика фикса Бага №1
не изменилась.

### 6. Мок-сервис онбординга

`bazar.onboarding.organizations / locations / memberships` отдельно от
моков Промта 3; чтение — объединение, данные Ивана не перезаписываются.
`addMembership` обновляет запись пользователя в `bazar.auth.users`,
поэтому `getSession()` отдаёт свежие членства без изменения контракта
аутентификации. // MOCK ONLY. Реальный бэкенд — Промт 7.

## Последствия

- Экраны входа не знают, куда вести пользователя: только guard.
- `logout` сбрасывает и онбординг-стейт: черновики не протекают между
  аккаунтами.
- Тесты экранов входа проверяют состояние стора, а не навигацию;
  маршрутизация покрыта тестами guard'ов и
  `post-auth-routing.test.tsx` (4 сценария Бага №2).
