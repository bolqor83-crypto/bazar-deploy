# ADR 0003: Навигация, оболочка и контекст

- **Статус:** принято (Промт 3)
- **Дата:** 2026-11-10

## Контекст

Один человек на аграрном рынке совмещает роли: владеет розничной точкой,
работает управляющим в чужом магазине, продаёт оптом и подрабатывает
перевозчиком. Мультиконтекстность — не экзотика, а норма. При этом оптовый и
розничный торговые контуры нельзя смешивать ни в UI, ни в данных (правило
AGENTS.md), а переключение роли не должно требовать повторного входа.

## Решение

### Модель контекста (5 уровней, не склеивать)

```
User → Organization → Membership → BusinessLocation → Role
```

- **User** — аккаунт для входа, один.
- **Organization** — бизнес-субъект (wholesale / retail / logistics), их много.
- **Membership** — связь User ↔ Organization с ролью в ней.
- **BusinessLocation** — торговая точка розничной организации.
- **Role** — `customer | store_owner | wholesale_seller | carrier`.

Активный контекст:

```ts
type ActiveContext = {
  userId: string;
  role: Role;
  organizationId: string | null; // null для customer
  locationId: string | null;     // только для store_owner; null = «вся сеть»
};
```

Правила по ролям: `customer` — без организации; `store_owner` — организация
обязательна, точка опциональна; `wholesale_seller` — организация обязательна,
точка не применима; `carrier` — логистическая организация опциональна.

**Почему не «один юзер = одна сфера»**: реальные пользователи совмещают роли
(владелец точки работает управляющим в другой сети), принудительный выбор
одной роли при входе ломает сценарий «утром закупка, днём отгрузка».

**Почему не классический multi-tenant**: у нас нет изолированных «тенантов» с
приватными данными на компанию. Публичная сцена (оптовый каталог) общая,
а контекст — это фильтр того, чем пользователь оперирует сейчас: какие
экраны, какие данные, какой tab bar. Переключение контекста — смена «точки
зрения», а не смена учётной записи.

### Переключение контекста

- Кнопка в шапке (`ContextSwitcher`) → нижний шит (`ContextSheet`): секции
  «Роль» (чипы), «Организация», «Точка» (+ «Вся сеть»), кнопка «Применить».
- «Применить» → `setActive` (с валидацией) → haptic selection → закрытие шита.
- Переключение меняет: набор вкладок tab bar, доступные экраны, заголовок
  шапки и данные (пока моки).
- Отдельного экрана логина для смены роли нет — контекст всегда под рукой.

### Маршруты Expo Router

```
src/app/
├── _layout.tsx            # шрифты + гидратация контекста + сплэш
├── (tabs)/
│   ├── _layout.tsx        # стек без заголовков (шапку рисует RoleShell)
│   ├── index.tsx          # редирект по активной роли
│   ├── customer/  (5)     # home, orders, deliveries, favorites, profile
│   ├── store/     (9)     # purchase, feed, storefront, orders, debts,
│   │                      # notes, finance, profile, settings
│   ├── wholesale/(9)      # overview, products, orders, requests, clients,
│   │                      # finance, analytics, profile, settings
│   └── carrier/  (5)      # feed, my-requests, in-transit, history, profile
├── dev/design.tsx         # витрина Промта 2 (только __DEV__)
└── +not-found.tsx
```

Каталоги ролей названы `customer/store/wholesale/carrier` (не длинными
именами ролей): Expo Router строит URL из имён файлов, а `orders` существует
у трёх ролей — префикс роли в пути обязателен, короткий префикс читабельнее.

### Tab bar по ролям

| Роль | Вкладки |
|---|---|
| customer | Главная · Заказы · Доставки · Избранное · Профиль |
| store_owner | Закупка · Лента · Витрина · Заказы · Ещё |
| wholesale_seller | Обзор · Товары · Заказы · Запросы · Ещё |
| carrier | Лента · Заявки · В пути · История · Профиль |

«Ещё» открывает шит с остальными разделами роли (store_owner: Долги, Заметки,
Финансы, Профиль, Настройки; wholesale_seller: Клиенты, Финансы, Аналитика,
Профиль, Настройки). Таб-бар кастомный (`BottomTabBar`), не дефолтный из
Expo Router — полный контроль стиля, высота 64 + safe area, зоны ≥ 48×48,
haptic selection.

### Состояние и персистентность

- `contextStore` (Zustand + persist): в AsyncStorage под ключом
  `bazar.context.active` хранится только `active`; `memberships` не персистятся
  (придут с API).
- При старте сохранённый контекст валидируется по членствам: роль исчезла или
  организация недоступна → откат на `customer`.
- До конца гидратации `_layout.tsx` держит сплэш и показывает Skeleton
  (спиннеры запрещены); `(tabs)/index.tsx` редиректит на первый экран роли.

### Моки

`apps/mobile/src/mocks/context.ts` — пользователь «Иван Петров», членства:
«Опт-Юг» (wholesale_seller, владелец), «Сеть „У дома“» (store_owner, владелец,
3 точки), «Магазин „Ромашка“» (store_owner, управляющий, 1 точка) +
«Транс-Логистик» (carrier) и режим customer. Членство-перевозчик добавлено
сверх минимального состава спецификации, чтобы роль carrier была достижима
в UI до появления API.

## Последствия

- Экраны-заглушки строятся только через `RoleScreen` (RoleShell + конфиг
  навигации): заголовок, вкладки и «Ещё» не дублируются.
- Опт и розница не смешиваются в одном tab bar: контуры разведены по контексту.
- Смена набора вкладок при переключении роли — следствие контекста, а не
  отдельной настройки.

## Открытые вопросы

- Реальная аутентификация (логин/пароль/OTP) — следующий промт.
- Передача контекста в API (заголовки вида `X-Bazar-Organization`) — следующий
  промт; пока все данные из моков.
- Полный экран управления точками/участниками организации — за рамками промта.
