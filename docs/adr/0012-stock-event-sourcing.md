# ADR 0012: Склад — event-sourced остатки (Промт 11)

Дата: 2026-11-15
Статус: принято

## Контекст

С Промта 8 остаток товара жил в колонке `ProductOffer.stock` —
просто число. Продавец объявлял «100 кг», продажи вычитали его, но:

- продажи вне Bazar не учитывались — остаток врал;
- не было истории: кто, когда и почему менял количество;
- не различались физический остаток, зарезервированный заказами
  и доступный к продаже;
- не было партий и нескольких складов.

Мастер-спека требует: «Склад — событийный (StockMovement), не
UPDATE stock SET qty». Промт 11 закрывает это до накопления
реальных данных (миграция числа в журнал безболезненна сейчас).

## Решение

### Event-sourcing: журнал + агрегат

- **StockMovement** — append-only журнал, источник правды. Каждое
  изменение остатка — запись: тип, дельта, причина (обязательна),
  актёр, ссылка на источник (`refType`/`refId`: order/manual/
  initial).
- **StockBalance** — денормализованный агрегат для быстрых
  запросов: `physicalQty` (физический остаток), `reservedQty`
  (резерв активных заказов), `availableQty = physical − reserved`
  (кэш для каталога/корзины). Пересчитывается в той же транзакции,
  что и запись журнала.
- **StockLocation** — склады организации (`WAREHOUSE`/`STORE`/
  `OTHER`); `@@unique([offerId, locationId])` на балансе —
  один остаток на пару оффер-склад.

### Семантика типов движений

| Тип                                         | physical | reserved | Доступность             |
| ------------------------------------------- | -------- | -------- | ----------------------- |
| INITIAL / RECEIPT / RETURN_IN / TRANSFER_IN | +q       | —        | +q                      |
| WRITE_OFF / TRANSFER_OUT                    | −q       | —        | −q (проверка ≥ q)       |
| RESERVED                                    | —        | +q       | −q (проверка ≥ q)       |
| UNRESERVED                                  | —        | −q       | +q                      |
| SALE_OUT                                    | −q       | —        | −q                      |
| ADJUSTMENT                                  | ±delta   | —        | ±delta (минус допустим) |

### Резервирование в заказах

- **Создание заказа** (PENDING): `RESERVED`-движения по складам
  продавца FIFO (по времени создания склада), каждое со ссылкой
  на заказ. Суммарно не хватает — `OUT_OF_STOCK`, транзакция
  создания откатывается целиком (ни одного заказа).
- **Подтверждение** (CONFIRMED): на каждый RESERVED-кусок — пара
  `SALE_OUT` (физический расход) + `UNRESERVED` (снятие резерва).
  Доступность не меняется (упала при резерве), физика списывается
  сейчас.
- **Отмена PENDING**: `UNRESERVED` по каждому куску — доступность
  возвращается.
- **Отмена CONFIRMED**: товар уже продан — `RETURN_IN` по каждому
  списанному куску.

### Правила

- Списания (`WRITE_OFF`/`TRANSFER_OUT`/`RESERVED`) не уводят
  доступный остаток в минус; `ADJUSTMENT` может — инвентаризация
  честно фиксирует недостачу.
- Перемещение — атомарная транзакция: `TRANSFER_OUT` +
  `TRANSFER_IN` парой; `from ≠ to`, оба склада организации.
- Причина обязательна (≥ 3 символов) — аудит читаем человеком.
- Ручные движения через API: только `RECEIPT`/`WRITE_OFF`/
  `ADJUSTMENT`; заказные типы — только из бизнес-логики.
- Default-склад «Основной склад» создаётся при onboarding
  организации и лениво при первом движении без явного склада.
- Склад удаляется только без движений (журнал неизменяем).

### Транзакционность

Пересчёт баланса сериализуется `SELECT ... FOR UPDATE` на строке
`StockBalance` (offer, location): конкурентные движения одного
остатка выстраиваются в очередь, потерянных обновлений нет.
Интерактивные транзакции — direct-подключение Neon (ADR 0010).

### Удалённое

- `ProductOffer.stock` — колонка удалена. Весь код читает
  `SUM(availableQty)` по складам (каталог, корзина, кабинет
  продавца).
- `StockChange` (Промт 10, previous/new) — таблица удалена:
  история вычисляется из движений (кумулятивная сумма дельт).
  Контракт `SellerOffer.stockChanges` сохранён для мобильного
  кабинета.

## Миграция (add_stock)

Снятие snapshot (pg_dump-эквивалент средствами Prisma, файл вне
репозитория) → одна транзакция:

1. Default-склад каждой организации (даже без офферов).
2. `ProductOffer.stock` → `StockBalance`: physical = stock +
   резервы активных заказов, reserved = резервы, available =
   stock (колонка хранила доступный остаток — вычет уже был).
3. `INITIAL`-движение на каждый непустой остаток.
4. `RESERVED`-движения на резервы активных заказов (PENDING/
   CONFIRMED) — подтверждение/отмена находят свои резервы.
5. Drop column `stock`, drop table `StockChange`.

Живых пользователей на момент миграции нет (демо-данные Ивана);
snapshot позволяет откатиться к дубликации схемы и данных.

## Последствия

- API `/api/stock/*`: locations CRUD, balances (list/get/summary),
  movements (list/create), transfer — под JWT + membership.
- Каталог: `bestOffer.stock` — вычисляется из балансов; нулевой
  доступный остаток скрывает оффер (как раньше stock=0).
- Уведомления продавцам: списание (WRITE_OFF) и обнуление
  доступного остатка (STOCK_EMPTY).
- Mobile UI склада — Промт 11b (экран остатков, ручные движения,
  перемещения, история).

## Открытые вопросы

- Партии (lot/batch) и сроки годности — Промт 11b+.
- Перемещение покупателю «из точки» — модель резерва под выдачу.
- Инвентаризация как отдельный процесс (сейчас — ручной
  ADJUSTMENT).
- Пересчёт балансов из журнала (компенсирующие транзакции при
  рассинхроне) — при росте объёма.
